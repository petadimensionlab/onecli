BYO エージェント発行手順

自分のマシンや CI で動かす「bring-your-own」エージェントを作成し、必要な資格情報だけを 付与して、onecli run で動かすまでの手順です。既存の hosted エージェントを BYO に置き換える場合の注意点と、PC 再起動後のチェックリストも含みます。

1. BYO とは（先に知っておくこと）

BYO エージェントは、OneCLI のサンドボックスではなく自分のマシン・CI・コンテナで 動かすエージェントです。ゲートウェイのプロキシトークンを利用者側が持つため、 onecli run や SDK で自分の環境に設定できます。

項目 BYO hosted
実行場所 自分のマシン / CI / コンテナ OneCLI のサンドボックス
トークン 利用者が取得・設定する サーバー側で注入（外部に出さない）
container-config API 取得できる 403 HOSTED_AGENT で拒否

kind と identifier は作成後に変更できません。 API の更新項目は name / instructions / model / effort のみです。hosted を BYO にしたい場合は作り直しが必要です。

CLI の onecli agents create は kind を指定しなければ 自動的に byo になります（--kind フラグはありません）。

2. 新規 BYO エージェントの発行

1

エージェントを作成する

onecli agents create --name "My Agent" --identifier my-agent

返ってきた JSON の id を控えます。

{
  "id": "779cfc4e-...",
  "name": "My Agent",
  "identifier": "my-agent",
  "isDefault": false
}
  • identifier は ^[a-z0-9][a-z0-9-]{0,49}$（小文字・数字・ハイフン）
  • ワークスペース内で一意。既存と重複すると 409
  • 別プロジェクトに作る場合は --project <slug>
2

資格情報（グラント）を付与する

作成直後は何も使えません。必要なシークレットと接続を明示的に付与します。

# シークレット（全許可のみ）
onecli agents grants attach-secret --id <agent-id> --secret-id <secret-id>

# 接続（引数なし = 全ツール許可）
onecli agents grants attach-connection --id <agent-id> --connection-id <conn-id>

# 接続をツール単位で絞る（未指定ツールはブロック）
onecli agents grants attach-connection --id <agent-id> --connection-id <conn-id> \
  --allow search_messages,get_message \
  --ask send_email
  • ID は onecli secrets list / onecli apps connections list で確認
  • --allow と --ask に同じツールは指定不可（422）
  • すべてブロックする指定は不可（外すなら detach）
3

このマシンに紐付ける

onecli config set agent my-agent

onecli run の解決順は次のとおりです。

優先度 指定方法
1（最優先）onecli run --agent my-agent
2環境変数 ONECLI_AGENT
3onecli config set agent
4プロジェクトのデフォルトエージェント

シェルで ONECLI_AGENT が設定されていると、config の pin を上書きします。echo "$ONECLI_AGENT" で確認してください。

4

動作確認する

onecli run --dry-run -- claude             # 設定解決の確認（実行しない）
onecli agents credentials --id <agent-id>  # 実効権限の確認
onecli run -- claude                       # 本番実行

ゲートウェイの資格情報注入まで確認するなら、認証が必要なエンドポイントを使います。 直接叩くと 401、ゲートウェイ経由で 200 なら成功です。 

onecli run -- curl -s -o /dev/null -w '%{http_code}\n' \
  https://openrouter.ai/api/v1/key

3. 既存 hosted を BYO に置き換える

インプレース変換はできません。次のどちらかを選びます。

A. 安全: 先に BYO を複製してから hosted を退役

# 1. 現状のグラントを控える
onecli agents grants list --id <hosted-id>
onecli agents credentials --id <hosted-id>

# 2. 別 identifier で BYO を作成
onecli agents create --name "My Agent (BYO)" --identifier my-agent-byo

# 3. 同じグラントを再付与し、pin を切り替えて検証
onecli agents grants attach-secret --id <new-id> --secret-id <secret-id>
onecli config set agent my-agent-byo
onecli run --dry-run -- claude

# 4. 問題なければ hosted を削除
onecli agents delete --id <hosted-id>

B. 同じ identifier を使う: 削除 → 再作成

identifier は一意なので、同じ名前を再利用するには先に削除が必要です。 削除するとサンドボックス、会話履歴、チャンネル連携、旧アクセストークンが失われます。 グラントもコピーされません。 

onecli agents delete --id <hosted-id>
onecli agents create --name "My Agent" --identifier my-agent
onecli agents grants attach-secret --id <new-id> --secret-id <secret-id>
onecli config set agent my-agent
onecli run --dry-run -- claude

4. トラブルシューティング

症状 原因 / 対処
403 HOSTED_AGENT“hosted sandbox; credentials are never handed out” 対象が kind = hosted です。BYO を作成し、その identifier に onecli config set agent で切り替えてください。hosted のままでは トークンは取得できません。
403“BYO agent creation isn't enabled for this organization” OneCLI Cloud で組織の BYO 作成が無効です。ダッシュボード/オンボーディングで 有効化するか、セルフホストを使用します（セルフホストは無制限）。
409“An agent with this identifier already exists” 同じ identifier が既にあります。別名にするか、既存を削除してから 再作成してください。
Could not resolve proxy: gateway サーバーがコンテナ内部向けのアドレスを返しています。セルフホストでは ONECLI_AGENT_PROXY_ADDRESS=host.docker.internal:10255 を docker/.env に設定して API を再作成すると、CLI が 127.0.0.1 に読み替えます。
Port number was not a decimal number（:10255:10255） CLI 2.11 系で --gateway host:port を渡すとポートが二重化します。 --gateway を付けず、デフォルト解決に任せてください。
意図しないエージェントが使われる ONECLI_AGENT が --agent と config より 優先されます。echo "$ONECLI_AGENT" を確認するか、明示的に --agent を渡してください。
ゲートウェイ経由だけ失敗する 直接叩いて 401、ゲートウェイ経由で 200 なら資格情報の 注入は成功です。両方失敗する場合はグラントとホストパターンを確認してください。

5. Tailnet 内の別 PC から利用する

OneCLI をホストしている PC 以外のマシンからも、同じ tailnet 経由でエージェントを実行できます。 エージェント本体は利用する PC 側で動き、設定の取得は API、外部通信はゲートウェイを 経由します。ホスト側に runner や追加の Docker コンテナは要りません。

用途 接続先
API（エージェント設定の取得・管理） http://<onecli-host>:10256
ゲートウェイ（エージェントの proxy） <onecli-host>:10255
Dashboard（任意） http://<onecli-host>:10254

<onecli-host> は OneCLI ホストの tailnet 上の IP または MagicDNS 名に 置き換えてください。IP は変わることがあるため、可能なら MagicDNS 名の利用をおすすめします。

CLI を使う（推奨）

  1. OneCLI ホスト側で API キーを確認します（他人に見せないでください）。 
    onecli auth api-key
  2. 別 PC に CLI をインストールします。 
    curl -fsSL onecli.sh/cli/install | sh
  3. API の向き先を OneCLI ホストに変更します。 
    onecli config set api-host http://<onecli-host>:10256

# 環境変数で指定する場合
export ONECLI_API_HOST=http://<onecli-host>:10256
  4. API キーでログインします。 
    onecli auth login --api-key oc_...
  5. エージェントを確認して実行します。 
    onecli agents list
onecli config set agent my-agent
onecli run --agent my-agent -- claude

サーバーが返す proxy アドレスは host.docker.internal:10255 ですが、 CLI が API ホスト名に自動で書き換えるため、別 PC 側で proxy を設定する必要はありません。

API を直接使う

curl -s "http://<onecli-host>:10256/v1/container-config?agent=my-agent" \
  -H "Authorization: Bearer $ONECLI_API_KEY" \
  -H "X-Project-Id: <project-id>" | jq .
  • レスポンスの env.HTTPS_PROXY にはエージェントの proxy トークンが含まれます。 トークンはログや画面に出さないでください。
  • API を直接使う場合、host.docker.internal は別 PC では解決できません。 env.HTTPS_PROXY のホスト部分を <onecli-host> に置換してください （CLI は自動で行います）。
  • TLS を検証する場合は、レスポンスの caCertificate を信頼ストアに追加します。
  • プロジェクトを明示する場合は X-Project-Id に onecli projects list の id を指定します。

Dashboard を別 PC から使う場合は、ONECLI_EXTERNAL_URL （または ONECLI_TRUSTED_ORIGINS）にダッシュボードの URL を設定する必要があります。 未設定のままだと、better-auth は localhost 以外の origin からのログインを拒否します。 CLI と API キーによる利用はこの制限を受けません。

公開範囲に注意してください。 セルフホストは既定で 0.0.0.0 で待ち受けるため、tailnet だけでなく LAN からも 到達できます。tailnet に限定するなら Tailscale ACL や ufw で 10254〜10257 番を tailscale0 のみ許可し、インターネットには公開しないでください。

  • API キーはユーザーの資格情報です。別の人に利用させる場合は、その人専用のユーザーと API キーを作成してください。
  • エージェントからモデルへの通信は、OneCLI ホストのゲートウェイを経由します。 別 PC からモデルへ直接到達できる必要はありません（ホスト側から到達できる必要はあります）。
  • 別 PC のコンテナ内でエージェントを動かす場合は、そのコンテナから <onecli-host>:10255 に到達でき、CA を信頼できるようにしてください。

6. Codex を ChatGPT OAuth（auth.json）で使う

API キー（sk-...）ではなく、ChatGPT のログイン（~/.codex/auth.json）で Codex を動かす手順です。OneCLI は auth.json を authMode: oauth として 自動判定し、エージェントには CODEX_HOME とダミーの auth.json を渡します。 実際のトークンはゲートウェイが注入し、期限切れ時は refresh token で更新します。

auth.json はパスワード同等です。 リポジトリやチャットに貼らず、パーミッションを 600 にしてください。

6.1 OAuth シークレットを作る

Codex を ChatGPT でログイン済みの PC で:

codex login
ls -l ~/.codex/auth.json

OneCLI に OAuth シークレットとして登録します。

onecli secrets create \
  --name "Codex OAuth" \
  --type openai \
  --file ~/.codex/auth.json \
  --host-pattern api.openai.com
  • サーバーが auth_mode: "chatgpt" と tokens を見て authMode: oauth を自動判定します
  • hostPattern は内部的に chatgpt.com に正規化されます
  • 返ってきた id を控えます

6.2 エージェントに付与し、API キーを外す

onecli agents grants attach-secret \
  --id <agent-id> --secret-id <oauth-secret-id>

onecli agents grants detach-secret \
  --id <agent-id> --secret-id <api-key-secret-id>

# 不要なら API キーのシークレットを削除
onecli secrets delete --id <api-key-secret-id>

確認:

onecli agents credentials --id <agent-id>

OAuth のシークレットだけが表示され、OPENAI_API_KEY が注入されなければ OK です。 

onecli run --agent codex --dry-run -- codex

CODEX_HOME が出て、OPENAI_API_KEY が出ないことを確認します。

6.3 クライアントの auth.json を OneCLI 管理用に置き換える

OneCLI の CLI は ~/.codex/auth.json が存在しない場合だけスタブを作ります。 既存ファイルは上書きしません。ChatGPT ログイン直後の本物の auth.json がある場合は、 id_token と account_id を残し、access/refresh だけを OneCLI 管理用に 差し替えます。 

cp ~/.codex/auth.json ~/.codex/auth.json.real

jq --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  '.OPENAI_API_KEY = null
   | .tokens.access_token = "onecli-managed"
   | .tokens.refresh_token = "onecli-managed"
   | .last_refresh = $now' \
  ~/.codex/auth.json.real > /tmp/codex-auth.json

mv /tmp/codex-auth.json ~/.codex/auth.json
chmod 600 ~/.codex/auth.json

置き換え後のイメージ:

{
  "auth_mode": "chatgpt",
  "OPENAI_API_KEY": null,
  "tokens": {
    "id_token": "<real-id-token>",
    "access_token": "onecli-managed",
    "refresh_token": "onecli-managed",
    "account_id": "<account-id>"
  },
  "last_refresh": "<ISO8601>"
}

id_token と account_id は、OneCLI に登録した auth.json と同じアカウントの値でなければなりません。別アカウントの値を作ると selected workspace missing from routing discovery の原因になります。

6.4 macOS で Keychain が優先される場合

Codex は macOS の Keychain に認証を保存し、~/.codex/auth.json より優先することが あります。その場合、ファイルを直しても古いアカウントが使われます。 

cat ~/.codex/config.toml
security find-generic-password -s "Codex Auth" 2>&1 | head -5

cli_auth_credentials_store が auto / keyring なら、 ファイル保存に固定します。 

# 既存行を置き換える
sed -i '' 's/^cli_auth_credentials_store *=.*/cli_auth_credentials_store = "file"/' \
  ~/.codex/config.toml

# 行がない場合
grep -q '^cli_auth_credentials_store' ~/.codex/config.toml 2>/dev/null || \
  printf '\ncli_auth_credentials_store = "file"\n' >> ~/.codex/config.toml

Keychain の古い項目が残っている場合は削除します。

security delete-generic-password -s "Codex Auth"

6.5 Codex のプロセスをすべて終了する

古い app-server が認証をメモリに持っていると、ファイルを直しても反映されません。 IDE の Codex 拡張も終了します。 

pgrep -fl codex
pkill -f 'codex'

6.6 OAuth で起動する

onecli run --agent codex -- codex

確認ポイント:

  • 起動時に OPENAI_API_KEY ではなく CODEX_HOME が使われる
  • ゲートウェイのログに chatgpt.com/backend-api/wham/accounts/check への 200 と injections_applied が出る
  • api.openai.com/v1/responses への 401 が出ない

6.7 selected workspace missing from routing discovery

このエラーは、Codex がローカルの auth.json から読んだ account_id を、 ChatGPT のアカウント一覧で見つけられないときに発生します。 

jq '{auth_mode, account_id: .tokens.account_id, access: .tokens.access_token}' \
  ~/.codex/auth.json

account_id が OneCLI の OAuth シークレットの metadata.accountId と 一致しているか確認します。一致していても直らない場合は、次を順に確認してください。

  1. ~/.codex/config.toml の cli_auth_credentials_store が "file" になっているか
  2. Keychain（Codex Auth）に古い認証が残っていないか
  3. Codex のプロセスをすべて終了したか
  4. ~/.codex/auth.json の id_token と account_id が同じアカウントか
  5. OneCLI のシークレットが、その auth.json から作られているか

6.8 API キー方式を完全に止める

onecli agents credentials --id <agent-id>
onecli secrets list
  • OAuth 以外の openai シークレットがエージェントに付いていないこと
  • シェルに OPENAI_API_KEY が残っていないこと （~/.zshrc / ~/.bashrc も確認）
  • ~/.codex/config.toml に API キーを強制する設定がないこと
unset OPENAI_API_KEY

ChatGPT の OAuth を使う場合、API プラットフォームの API キーは不要です。API キーの シークレットを削除すれば、誤って API キー方式に戻ることはありません。

付録: PC 再起動後のチェックリスト

コンテナは restart: unless-stopped で、Docker サービスが有効なら 再起動後に自動で立ち上がります。設定ファイル（.env）を触る必要はありません。 

# 1. Docker とコンテナの状態（起動直後は数十秒待つ）
docker ps

# 2. 起動していない場合だけ、compose ファイルのあるディレクトリから起動
cd ~/onecli/docker
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d

# 3. ダッシュボードと API の疎通
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:10254/auth/login   # 200

# 4. CLI の認証と pin
onecli auth status
onecli config get agent

# 5. ゲートウェイ経由の実リクエスト（200 なら成功）
onecli run -- curl -s -o /dev/null -w '%{http_code}\n' \
  https://openrouter.ai/api/v1/key

コンテナを再作成するときは、必ず docker/ ディレクトリで docker-compose.yml と docker-compose.build.yml の両方を指定してください。 リポジトリ直下の .env はローカル開発用で、スタックの認証シークレット （BETTER_AUTH_SECRET 等）とは別物です。誤った組み合わせで再作成すると、 ログインセッションが無効になります。
